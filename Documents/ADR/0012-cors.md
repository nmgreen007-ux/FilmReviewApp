# ADR-0012: CORS Policy

## Status
Accepted

## Context
The React SPA and the .NET API are served from different origins — the frontend runs on a separate port (or in production, a separate domain) to the API. Browsers enforce the Same-Origin Policy, which blocks cross-origin requests unless the server explicitly opts in via CORS headers.

A CORS policy was needed that:
- Allows the frontend SPA to call the API
- Does not expose the API to arbitrary third-party origins
- Works consistently across local development and production environments without code changes

## Decision
A named `AllowFrontend` policy is registered in `Program.cs`:

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("AllowFrontend", policy =>
    {
        policy.WithOrigins(builder.Configuration["AllowedOrigins"] ?? "https://localhost:5173")
            .AllowAnyMethod()
            .AllowAnyHeader();
    });
});
```

The allowed origin is read from the `AllowedOrigins` key in `appsettings.json`, defaulting to `https://localhost:5173` for local development. All HTTP methods and headers are permitted. The policy is applied globally via `app.UseCors("AllowFrontend")`, positioned before authentication and authorisation middleware.

## Reasons
- **Config-driven origin:** Reading the allowed origin from configuration means the same compiled code works in local development and in production — the deployed environment provides a different `AllowedOrigins` value via environment-specific settings or environment variables. No code change is required to switch environments.
- **Named policy:** Using a named policy (`AllowFrontend`) keeps the intent explicit and makes it straightforward to apply different policies to different endpoint groups in future if needed.
- **AllowAnyMethod / AllowAnyHeader:** The API is a controlled, first-party service called exclusively by the SPA. Restricting methods to `GET` and `POST` would add maintenance burden with no meaningful security benefit — the API's own authorisation attributes and validation are the real security boundary.

## Alternatives Considered
- **Hardcoded origin:** Hardcoding `https://localhost:5173` was rejected because it would cause CORS failures in any non-local environment without a code change.
- **AllowAnyOrigin:** Allowing all origins was rejected as unnecessarily permissive. The only legitimate caller is the known SPA — there is no reason to permit arbitrary third-party origins to call the API.
- **Credentials (AllowCredentials):** Not required. The application uses bearer tokens via the `Authorization` header, not cookies. `AllowCredentials()` is only necessary for cookie-based cross-origin flows.

## Consequences
- The API accepts cross-origin requests from the configured frontend origin only
- Changing the allowed origin in a new environment requires only an `appsettings` change, not a code change
- CORS is applied before authentication middleware, ensuring preflight `OPTIONS` requests are handled correctly without requiring a bearer token
